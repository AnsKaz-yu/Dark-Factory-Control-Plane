# Предложения по развитию плагина reservoiros-dashboard

> Что ещё добавить для эффективного контроля за проектом ReservoirOS. Приоритеты:
> P0 — критично для контроля, P1 — полезно, P2 — дифференциатор.

## P0 — критично для контроля

### 1. Интеграция статуса гейтов (G1–G6) в дашборд
Сейчас дашборд показывает CRAP/покрытие/задачи, но не статус гейтов harness. Добавить
панель гейтов per-component: G1 C4, G2 TDD, G3 CRAP, G4 oracle, G5 build, G6 чистота —
pass/fail/skip из отчётов harness (`reports/gates-summary.json`, `evidence/`). Источник:
`scripts/gates.ps1` уже пишет сводку — плагин читает её и показывает红绿灯 на компоненте.
**Ценность**: видно, какой компонент не проходит гейты (блокер релиза).

### 2. Критический путь и блокировки
Подсветка критического пути (самая длинная цепочка зависимостей до релиза) в графе задач.
Алерты: задача блокирует N других; «бутылочные горлышки». Авто-детект циклов зависимостей.
**Ценность**: фокус на задачах, которые разблокируют больше всего работы.

### 3. Requirement traceability (REQ → задачи → компоненты → тесты)
Матрица трассировки: каждое требование REQ-01..23 → покрывающие задачи → компоненты →
тесты/оракулы. Видно непокрытые требования (дыры в реализации). Клик по REQ → все связанные
задачи и их статус. **Ценность**: гарантия полноты (REQ-02/03), контроль скоупа.

### 4. Burndown / velocity и прогресс этапов
График завершения задач во времени (burndown), velocity (задач/неделю), прогресс этапов
roadmap (0–7). Прогноз даты завершения по текущей velocity. **Ценность**: предсказуемость
сроков, раннее обнаружение отставания.

## P1 — полезно

### 5. Тренды CRAP и покрытия (sparklines + регресс-алерты)
История CRAP/покрытия per-component (sparkline), алерт при регрессии (CRAP вырос, покрытие
упало). Хранить историю в `project-state.json` (кольцевой буфер) или отдельном файле.
**Ценность**: контроль деградации качества, не только текущий срез.

### 6. Oracle-дашборд (точность vs эталон)
Per-domain max relative error vs порог (blackoil/comp/thermal) из `oracle/reports/`.
Тренд точности, алерт при превышении порога. **Ценность**: контроль REQ-03 (точность)
в реальном времени.

### 7. Risk heatmap
Тепловая карта риска: компонент = f(высокий CRAP, низкое покрытие, заблокированные задачи,
непройденные гейты). Топ рисковых компонентов. **Ценность**: приоритизация усилий.

### 8. Балансировка нагрузки агентов
Задач на агента, загрузка, простаивающие агенты / перегруженные. Рекомендации по
перераспределению. **Ценность**: эффективная параллельная работа.

### 9. Уведомления / алерты
При событиях: задача разблокирована, гейт упал, CRAP > 30, покрытие упало, агент простаивает.
Интеграция с OpenCode (synthetic message) или внешний канал. **Ценность**: проактивный
контроль вместо ручного просмотра.

## P2 — дифференциатор

### 10. What-if симуляция
«Что если задержать задачу X?» — влияние на критический путь и дату релиза. Перетаскивание
задач в графе для перепланирования. **Ценность**: планирование и оценка рисков.

### 11. Экспорт снапшотов (HTML/PDF)
Снимок дашборда для отчётов (интеграция с dev-pr-report-html). История снапшотов по майлстоунам.
**Ценность**: отчётность перед руководством.

### 12. Интеграция с Jenkins
Статус сборок Jenkins (build #, success/failure) per-component, ссылка на консоль.
**Ценность**: единая картина CI + реализация.

### 13. Time tracking / estimates vs actual
Оценка vs фактическое время по задачам, калибровка оценок. **Ценность**: точность планирования.

### 14. Авто-обновление из артефактов
Плагин сам читает отчёты cargo-crap/llvm-cov/gcovr/oracle/gates и обновляет состояние без
ручного вызова инструментов (file-watch на reports/). Агент только пишет код — метрики
подтягиваются автоматически. **Ценность**: минимум ручных действий, актуальность.

## Рекомендуемый порядок внедрения
1. **P0.1** (гейты) + **P0.3** (traceability) — максимальная ценность для контроля при
   минимальных усилиях (данные уже есть в harness).
2. **P0.2** (критический путь) + **P1.5** (тренды) — контроль рисков и деградации.
3. **P1.6** (oracle) + **P1.9** (алерты) — проактивный контроль точности.
4. Остальное по мере необходимости.

## Технические заметки
- История метрик: кольцевой буфер в `project-state.json` (последние N точек) — без раздувания.
- Авто-обновление (P2.14): file-watch на `ReservoirOS-harness/reports/` и
  `ReservoirOS/architecture/evidence/`; парсеры отчётов уже есть (gates-summary.json, suite-report.json).
- Все предложения сохраняют принцип: модель отделена от рендера, real-time через SSE.
